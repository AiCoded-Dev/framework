# E-MIG-004: migrations that differ from what the database ran

A database keeps the steps of migrations it ran in its journal, the table `aicoded_migrations`: their place, publish, place in the publish and hash. A release's list of steps must start with the journal's, or, for a rollback to an older release, be the start of it. Here the two differ: the release comes from another line of publishes than the one live, or someone changed the database or its journal by hand. A list whose steps are not numbered from 1 or whose hash does not match its statement, or one over 2000 steps or 1 MiB of statements, is refused the same way. Nothing was applied. In `aicoded dev` the dev database is made again instead, since its data is test data.

On the platform a release is also refused with this code after a step failed on production data (see E-MIG-005): when its publish holds the schema changes that were rejected then, which are never released, and when its migrations differ from those that ran in production. Put a corrected version of the unreleased changes in `.aicoded/migration.sql`, leaving out the steps that ran, and publish again: the new publish's migrations start with the ones that ran.

**Fix:** release a publish made on top of the one live, so that its migrations start with the ones the database ran; after a step failed on production data, publish again with a corrected draft; a database changed by hand needs the platform's operator
