# E-MIG-005: a step of the migrations failed

A step failed while it was applied to the database: MySQL refused its statement, the statement waited more than 30 seconds for a table that another session used, it ran for more than 5 minutes, or another applier of the same database held its migration lock for more than 60 seconds. A connection with no database selected is refused the same way. The message names the step as `<publish>#<index>`. The steps before it stay applied and in the journal; the step and those after it are not.

On the platform the release stops and the version that runs keeps serving. The message names the step and MySQL's error number, with a fixed short text for the common ones, such as `MySQL error 1062 (duplicate key)`, and never MySQL's own message, which can quote the data in the app's database. What happens next depends on why the step failed:

- **MySQL refused the statement on production data**, as with a unique key over rows that repeat a value, a `NOT NULL` column over rows that hold `NULL`, or a value that does not fit. The steps that ran in production stay as they are. The schema changes after them are rejected: no publish that holds them is ever released, and `aicoded status` and the `release_status` tool show this error on each such publish, with the step. The app's migrations become the ones that ran in production. Put a corrected version of the unreleased changes in `.aicoded/migration.sql`, leaving out the steps that ran, and publish again. `aicoded dev` makes the dev database again from the app's migrations and the new draft.
- **The step could not finish**: a lock wait, a deadlock, a time limit, a broken connection or the state of the database server. Nothing is rejected: the publish shows this error as a note, and the next release tries the step again.
- **The step ran but was not recorded**: its statement ran, but its row could not be added to the journal, even after two more tries on new connections under the database's migration lock, as when the connection breaks right after the statement. The message says `ran but was not recorded`. Nothing is rejected: the publish shows this error as a note. Since the next release would run the step again, the platform's operator adds the step's row to the journal before it; nothing in the app needs to change.

In `aicoded dev` and `aicoded check` the message also quotes MySQL's own message, since the data there is test data.

**Fix:** the change failed on production data: put a corrected version of the unreleased changes in .aicoded/migration.sql and publish again; when it could not finish in time, it is tried again with the next release; in aicoded dev, change the draft, or start the app again once the table is less busy
